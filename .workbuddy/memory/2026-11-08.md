## 更正：504 是间歇性的，不是该路径整体下线

- 18:13 复测（Range bytes=0-1023，各 5 次）：默认 curl 5 次里 2 次 504 / 3 次 206；
  强制 `--http1.1` 5 次里 2 次 504 / 3 次 206 → 协议不是关键，约 40% 请求随机命中 504。
  504 响应 92 字节 HTML、`Via: 2.0 Caddy`、`X-Github-Edge-Region` 每次不同
  （japaneast / koreacentral / uaenorth），是中间网关/边缘节点超时；HEAD 到 github.com
  短链能正常返回 302 签名直链。本机与 Windows 均确认无系统代理。
- 所以「换 API asset 端点就通」只是恰好命中好节点。用户用 IDM 能下成功的原因是
  多连接分段 Range + 自动重试 + 断点续传 + 浏览器 UA/Referer/已解析直链，
  把约 40% 的单次失败率吃掉了；CI 的 curl 是单连接整包 274 MB、`--retry 5`（共 36 s）、
  无 `--fail`（504 页面被当作成功写入 zip）、无续传，撞上一串 504 就挂。
- 修法排序：① 分段/续传下载（Range 分块或 aria2c -x8，`-fL -C -` 循环到精确字节数
  274281827 / 280810851）+ sha256 校验 + `--fail` + 打印实际大小；
  ② 把工具链作为 workflow artifact 传一次给两条 lane 复用（Actions 内部存储，绕开 release CDN）；
  ③ 仅换 URL 不够，必须同时加容错。

## 追问：为什么 UCRT/官方 LLVM 不缺这两个库，MinGW 缺

- 解析本地 `lib/rt/lib/win{32,64}/libfb.a` 的 ar 成员：**只有 `io_printerwin.o`
  引用 winspool/gdi32 符号**（OpenPrinterA/CreateDCA/TextOutA/W/WritePrinter...）。
  win64 `io_fileopen.o` 里的 "ClosePrinter" 只是本地函数名 `hClosePrinterHandle`，
  不是导入。runtime 的按需拆分有效 → 控制台程序产物不导入 WINSPOOL.DRV/GDI32.dll。
- 两条链接线其实**都**列了这两个库：`src/codegen/toolchain.tiko:1021`（MSVC/UCRT，
  `-nostdlib` 后显式补 9 个 `-l`，含 winspool/gdi32）与 `:1039`（GNU/COFF，
  无条件 `-lwinspool -lgdi32`）。差别不在 CRT 风味，在库的来源与解析方式：
  - MSVC/UCRT 侧：整套 import library 随仓库自带 —— `lib/implib/*.def`（827 个 DLL
    导出表）经 `build/implibs.sh` + llvm-dlltool 生成 843 个
    `toolchains/tiko-windows/lib/windows-x86_64/*.lib`；README 明说不需要 fbc 或
    MinGW tree。`winspool.lib`/`gdi32.lib`/`ucrtbase.lib`/`kernel32.lib` 全在，
    路径确定，无需猜 sysroot。官方 LLVM for Windows 同理走 MSVC driver，默认库由
    VC/Windows SDK 通过 `/DEFAULTLIB`（`#pragma comment(lib)`）注入，命令行不可见，
    SDK 里必有这些 .lib，所以从不报"找不到"。
  - MinGW 侧：driver 没有 SDK/defaultlib 机制，把库名硬拼成 `-lxxx`；ld/lld 对
    **每个 -l 都要求 libX.a 文件真实存在**，哪怕零符号被用。tiko 又无条件追加两个
    -l（为 `OPEN "LPT:"` 拉入 io_printerwin.o 时备用；fbc 是按 LPRINT 按需加）。
    于是所有 GNU 程序都被前置要求能找到这两个文件；clang 20 把 -L 指到
    `C:\msys64\mingw32\i686-w64-mingw32\lib`（MSYS2 没有该目录）就整串报错。
- 结论：「链接线上有」≠「exe 依赖 DLL」；`-nostdlib` 分支实测 hello world 只导入
  ucrtbase.dll + KERNEL32.dll，正是列 9 个 -l 只用到 2 个。用户的"不该参与"在
  产物层面本就成立；直接删 -l 会破坏 `OPEN "LPT:"`（LPRINT 在 -lang fb 是
  IFORM_UNSUPPORTED，LPT 设备名是运行时字符串，编译期无法可靠检测）。
- **同源发现**：`lib/win32/` 与 `lib/win64/` 里本来就有 `libgdi32.a`/`libwinspool.a`
  （win32 还有 `libfb_noprinter.a`，源码无引用，疑为历史产物），但被 `.gitignore`
  忽略 → 干净 checkout 没有，才被迫去 sysroot 找。与上一轮 fbrt0.o 的洞同源。
  更干净的修法是让 GNU 目标也自带 import library，而非让 clang 猜 sysroot。

## 实测（本地 D:/tiko-test/llvm，clang 21.1.3）根因定位

- 用户已有对照实验在 `D:/tiko-test/progs/`：用 `llvm-readobj --coff-imports`
  扫全部 exe → `u64` 系列（系统 UCRT，api-ms-win-crt-*.dll）、`t1_seed64.exe`
  （tiko 的 `-nostdlib -lucrtbase`，只导入 ucrtbase.dll + KERNEL32.dll）、
  `w64n`/`t1_np.exe` 都没有 GDI32/WINSPOOL；而 `w64r`/`t1_w64`/`t1_lp.exe`/
  `agg.exe` 等 GNU 产物**真的导入** GDI32.dll + WINSPOOL.DRV。
  → 上一轮「产物层面本就没有依赖」的判断错了一半，用户是对的。
- `clang -###` 实测：GNU driver 自动拼的是 `-lmingw32 -lgcc -lgcc_eh -lmoldname
  -lmingwex -lmsvcrt -ladvapi32 -lshell32 -luser32 -lkernel32`（**无 winspool/gdi32**，
  是 tiko 在 toolchain.tiko:1039 自己追加的）；MSVC driver 裸跑会带
  `-defaultlib:libcmt/oldnames` + VC/SDK libpath，但 tiko 的 UCRT 目标用
  `-nostdlib` 全关掉，靠 `lib/implib/*.def` → 843 个自带 .lib 和系统 DLL 导出的
  ucrtbase.lib，确实**不依赖 VC 编译器**（用户纠正，上一条解释有误）。
- **真正的根因是 tiko-rt 自己的静态引用链**，`llvm-nm -A` 坐实：
  `io_openqb.o` / `io_fileopen.o` → `U fb_DevLptOpen` → `io_devlptopen.o`
  → `U fb_PrinterOpen` → `io_printerwin.o` → `U OpenPrinterA/CreateDCA/
  TextOutA/WritePrinter/EnumPrintersA` → libwinspool.a / libgdi32.a 成员 → IAT。
  源码位置：`lib/rt/src/io/openqb.tiko:174` 与 `:181` 把 `@tkrt_DevLptOpen`
  当函数指针写进核心 QB-OPEN 路径，不管程序有没有 `OPEN "LPT:"`。
  `t1x.map` 里能看到 io_devlptopen.o / io_printerwin.o / libwinspool*.o /
  libgdi32*.o 全被拉入。四种归档（win32 / win64 / win64ucrt /
  toolchains windows-x86_64 的 libfb.a）都有这条链，所以**与 CRT 风味、LLVM
  版本、VC 无关**；删 -l 只会变成 undefined，不会消掉依赖。
- `lib/win32/libfb_noprinter.a` 是对照产物：从 214 个成员里剔除 7 个
  （io_devlptio/devlptopen/devlpttest/lpos/lprint/**openqb**/printerwin），
  导入表立刻干净 —— 但连 QB 形式 OPEN 一起没了，不是生产解。
- 正解方向：把 `io_openqb.o` 里的 LPT/PRN 分支拆成独立成员或改成运行时解析，
  让核心 file layer 不再静态引用 `fb_DevLptOpen`。属 tiko-rt 代码改动，
  需跑全套差分（runtime 是 fbc 逐行移植，不能随意"改良"）。
  注：纯静态链接下「拆分支」无法保住 LPT 功能（openqb.o 仍会强引用
  fb_DevLptOpen），最终选的是下面这条运行时解析路线。
